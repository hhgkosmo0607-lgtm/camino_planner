# B. 지도 데이터 — 어디서 가져왔고, 무엇을 했나

> **이 문서는 무엇인가**: `data/towns.ts`(마을 82곳)와 `data/profiles.ts`(구간 81개 고도), `data/forks.ts`(갈림길 11곳), `data/restaurants.ts`(식당·바·카페 1,247곳, 8절)를 만들 때 실제로 어떤 지도·고도 데이터를, 어떤 API로 가져와서, 어떻게 계산했는지를 순서대로, 쉽게 설명한다.
> 더 깊은 기술적 배경(왜 이 방식을 골랐는지의 근거·비교 실험)은 `DEVLOG.md`(2026-07-24~25 항목들)에, 원래 계획 문서는 `03_제품과기능.md` 부록에 있다. 이 문서는 그 둘을 종합해 **"결국 무엇을 썼고 무슨 일이 있었나"만 한 곳에서 보기 쉽게** 정리한 것이다.

## 1. 한눈에 보기

```
① 길의 모양(좌표)         ② 땅의 높이(고도)
   OpenStreetMap             EU-DEM 25m (Copernicus)
   (Overpass API로 조회)      (Open Topo Data API로 조회)
        │                          │
        └──────────┬───────────────┘
                    ▼
        길을 100m 간격으로 잘게 쪼개서
        각 지점의 높이를 다 더한다
        (스무딩 처리 포함 — 3장 참고)
                    ▼
        data/profiles.ts
        (구간별 실제 오르막/내리막 숫자만 저장)
```

**핵심은 "고도가 포함된 GPX 파일을 어디서 구하지 않았다"는 것이다.** 그런 파일은 대부분 출처가 불분명하거나 상업적 이용이 금지돼 있다. 대신 **① 길의 모양**과 **② 땅의 높이**를 서로 다른 무료·공개 출처에서 각각 가져와, **우리가 직접 계산**했다. 이렇게 하면 출처가 항상 명확하고, 계산 방식(스무딩 등)을 우리가 통제할 수 있다.

### 1.1 이건 "제대로 된 API"인가 — 그렇다

`data/albergues.ts`(숙소, `C_숙소카드교통데이터.md` 2절)나 `data/landmarks.ts`(안개 지도)는 Gronze.com·순례 가이드 사이트를 **사람이 읽고 옮겨적는 방식**(스크래핑 성격)으로 채웠지만, 지도·고도 데이터는 다르다 — **문서화된 공식 API를 코드가 직접 호출**했다.

| API | 문서 | 인증 | 비용 |
|---|---|---|---|
| **Overpass API** | https://wiki.openstreetmap.org/wiki/Overpass_API | 불필요 | 무료 |
| **Open Topo Data** | https://www.opentopodata.org/ | 불필요 | 무료 (공개 인스턴스, 예의상 초당 1회 제한 준수) |

두 API 모두 OSM 진영이 유지보수하는 공개 표준 API라 "제대로 된 API가 없어서 어쩔 수 없이 사람이 긁었다"는 숙소 쪽 사정과는 성격이 다르다. 실제 호출 코드는 `scripts/pipeline/build_geometry.py`의 `overpass()`(6개 relation 조회, `curl` 서브프로세스 호출 — `urllib`은 이 환경에서 막혀 우회)와 `fetch_elevations()`(좌표 배열을 Open Topo Data에 배치 조회) 함수를 참고.

## 2. 길의 모양은 어디서 왔나 — OpenStreetMap

### 2.1 OpenStreetMap이 뭔가

**OpenStreetMap(OSM)**은 전 세계 자원봉사자들이 함께 만드는 무료 지도 데이터베이스다(위키백과의 지도 버전이라고 생각하면 된다). 도로·오솔길·건물 같은 것들이 좌표로 등록돼 있고, 누구나 내려받아 쓸 수 있다.

카미노 데 산티아고 같은 유명한 도보길은 OSM 안에 **"하이킹 루트(hiking route)"**라는 특별한 묶음(relation, "관계")으로 등록돼 있다. 하나의 relation 안에는 실제 오솔길·도로 조각(way, "선")이 수백~수천 개 들어있다 — 마치 목걸이 하나(relation)가 구슬 여러 개(way)로 이어진 것과 비슷하다.

### 2.2 어떻게 가져왔나 — Overpass API

OSM 데이터베이스에 "이 조건에 맞는 데이터를 줘"라고 질문(질의, query)을 던지는 창구가 **Overpass API**다. 우리는 여기에 "프랑스 길에 해당하는 relation을 줘"라고 요청해서 실제 좌표들을 받았다.

- 사용한 주소(mirror, 여러 개의 동일 서버 중 하나): `overpass.kumi.systems`, `overpass-api.de`
- 실제로 가져온 relation 6개(카미노 프랑스 길은 하나의 relation이 아니라 6개 구간으로 나뉘어 있었다):

| relation ID | 구간 |
|---|---|
| 2163569 | 생장피드포르 → 로그로뇨 |
| 2163558 | 로그로뇨 → 부르고스 |
| 2163560 | 부르고스 → 레온 |
| 2163561 | 레온 → 카카벨로스 |
| 2163565 | 카카벨로스 → 팔라스 데 레이 |
| 2163559 | 팔라스 데 레이 → 산티아고 |

### 2.3 조각을 이어붙이기 (스티칭)

Overpass에서 받은 way 조각들은 **순서가 뒤섞여서** 온다. 그래서 "끝점이 서로 맞닿는 조각을 계속 이어붙이는" 작업(스티칭, stitching)이 필요했다 — 실뭉치를 풀어서 한 줄로 잇는 것과 비슷하다. 이 작업은 `scripts/pipeline/build_geometry.py`의 `stitch()` 함수가 한다.

**결과**: 6개 구간을 다 이어붙이니 총 **767.5km**가 나왔다. 가이드북 기준 거리(773.1km)와 **0.7%**밖에 차이 나지 않아, 제대로 이어졌다는 걸 확인할 수 있었다.

### 2.4 이 데이터의 라이선스 — ODbL

OSM 데이터는 **ODbL(Open Database License)**이라는 라이선스를 쓴다. 조건은 두 가지다.

| 조건 | 뜻 |
|---|---|
| 저작자 표시 | "© OpenStreetMap contributors"를 화면에 표시해야 한다 |
| 동일조건변경허락 | 이 데이터를 가공해서 "데이터베이스 그 자체"로 다시 배포하면, 그것도 ODbL로 공개해야 한다 |

**그래서 우리가 한 일**: 좌표 원본은 저장소에 올리지 않고(`data/geometry/`는 `.gitignore` 처리), 좌표로 계산한 **결과 숫자(오르막·내리막 m)만** `data/profiles.ts`에 남겼다. 좌표 자체를 재배포하는 게 아니라 "그 좌표로 계산한 결과물"만 남기는 것이므로 ODbL의 "데이터베이스 재배포" 의무를 피할 수 있다는 판단이다. 화면에는 항상 "경로 데이터 © OpenStreetMap contributors (ODbL)"를 표시한다.

## 3. 땅의 높이는 어디서 왔나 — EU-DEM 25m

### 3.1 왜 "GPX 파일의 고도"를 안 믿나

스마트폰이나 GPS 워치가 기록하는 고도는 기압계·위성 신호로 추정한 값이라 오차가 크다. 그래서 우리는 **DEM(Digital Elevation Model, 수치표고모델)**이라는, 위성이나 항공 측량으로 만든 별도의 "고도 지도"에서 좌표별 높이를 따로 조회했다.

### 3.2 최종적으로 쓴 것 — EU-DEM 25m

| 항목 | 내용 |
|---|---|
| 데이터 이름 | EU-DEM (European Digital Elevation Model) |
| 제작 | 유럽 Copernicus 위성 프로그램 |
| 격자 크기 | 25m (땅을 가로세로 25m 칸으로 나눠 칸마다 높이 하나) |
| 라이선스 | CC BY (출처만 밝히면 자유롭게 사용 가능) |
| 조회 API | **Open Topo Data** — 무료 공개 API. 주소: `api.opentopodata.org/v1/eudem25m` |

호출 예시(실제로 쓴 것과 같은 형태): 위도·경도를 넣으면 그 지점의 고도(m)를 돌려준다. 100m 간격으로 잘라낸 좌표 7,677개를 이 API에 순서대로 물어봤다(공개 API라 초당 1회 정도로 예의를 지켜가며 호출).

### 3.3 ⚠️ 원래는 IGN 5m를 쓰려 했다 — 근데 반대 결과가 나왔다

CLAUDE.md에는 원래 **스페인 국립지리원(IGN)의 MDT05(5m 격자, 항공 LiDAR 기반)**를 쓰기로 돼 있었다. "격자가 더 촘촘하니 더 정확하겠지"라는 가정이었다. 그런데 실제로 IGN 5m 데이터를 받아 비교해보니 **정반대**였다.

| 구간 | IGN 5m | EU-DEM 25m | 실제(추정) |
|---|---|---|---|
| 피레네 1일차(가장 가파른 구간) | **+2,355m** | **+1,327m** | **약 1,280m** |
| 완만한 평지 구간(대조군) | +112m | +108m | (둘 다 비슷) |

**평지에서는 5m든 25m든 거의 똑같은데, 가장 가파른 구간에서만 5m가 실제의 거의 두 배로 부풀었다.** 이유는: 5m 데이터는 미세한 요철까지 다 담는데, 우리가 따라가는 "길 좌표" 자체에 원래 몇 m~몇십 m의 오차가 있다. 가파른 비탈에서는 옆으로 조금만 어긋나도 높이가 크게 튀는데, 5m 데이터는 이 튐(노이즈)을 그대로 다 반영해버린다. 25m 데이터는 애초에 넓게 뭉뚱그려 재기 때문에 이 노이즈가 자동으로 눌린다.

**독립적으로 만들어진 데이터 3개**(EU-DEM·SRTM(미국 레이더)·ASTER(미·일 위성 광학))를 같은 지점에서 비교했더니 셋 다 1,309~1,327m로 모였고 IGN 5m만 2,355m로 혼자 떨어졌다 — 그래서 "EU-DEM 25m가 더 실용적으로 정확하다"고 결론 냈다.

> 📌 그래서 스키마의 `source` 값은 `'OSM+EUDEM'`이다. `'OSM+MDT'`(IGN용)는 나중에 실제로 IGN 5m를 쓰게 될 경우를 대비해 이름만 예약해뒀다.

### 3.4 오르막·내리막 계산 — 스무딩이 왜 필수인가

고도 값을 그냥 다 더하면(가공 없이) 미세한 요철·측정 오차까지 전부 "오르막"으로 잡혀서 실제보다 훨씬 크게 나온다(이번 검증에서 가공 없이 더하면 14% 더 크게 나왔다). 그래서 두 가지 처리를 했다.

1. **이동평균**: 앞뒤 5개 지점의 높이를 평균 내서 뾰족한 튐을 눌러준다.
2. **히스테리시스 임계값**: "3m 이상 방향이 바뀌어야 그제서야 오르막/내리막으로 인정"하는 규칙(등산 앱들이 실제로 쓰는 표준적인 방식).

이 두 함수(`_moving_avg`, `clean_gain_loss`)는 `scripts/pipeline/build_geometry.py`에 있고, 갈림길 데이터를 계산할 때도 그대로 재사용할 수 있게 만들어뒀다.

## 4. 마을 82곳의 좌표는 어떻게 구했나

마을 이름을 지도 검색(지오코딩)에 넣어 좌표를 받는 방법(예: Nominatim — OSM의 무료 지오코딩 서비스)을 먼저 시도했지만, **동명 마을이 여러 곳에 있어서 엉뚱한 위치가 나오는 문제**가 있었다(예: "레온"을 검색하면 카미노와 무관한 다른 레온이 나올 수 있다).

그래서 대신 **비율 계산** 방식을 썼다: 가이드북에 이미 적힌 "이 마을은 출발점에서 몇 km 지점"이라는 값과, 우리가 실측한 전체 경로 길이(767.5km, 가이드북 773.1km와 0.7%밖에 안 다름)의 비율을 이용해 "전체의 몇 % 지점"을 길 위에서 직접 찾았다. 검증해보니 팜플로나·부르고스·레온·사리아·산티아고 등 실제 도시 중심과 **최대 1.1km 이내**로 맞았다.

**마을의 거리(km)·고도(elevation) 원본 값은 이 방식으로 새로 만든 게 아니라, 이미 검증된 원본(`src/camino-companion.jsx`)의 값을 정규식으로 그대로 읽어와 보존했다** — 새로 계산해서 덮어쓰면 오히려 오차가 생길 위험이 있어서다. 이번에 새로 채운 건 원본에 없던 `lat`/`lng`(위도·경도)뿐이다.

## 5. 지어낸 데이터가 아님을 어떻게 확인했나 (검증)

카미노에는 누구나 아는 유명한 지점들이 있다. 우리가 API로 받은 고도가 이 알려진 값과 맞는지 대조했다.

| 지점 | 우리 측정값 | 알려진 실제값 |
|---|---|---|
| 철의 십자가(최고점) | 1,510m | 1,505m |
| 팜플로나 | 452m | ~450m |
| 산티아고 | 255m | ~260m |

또한 고도 값의 표준편차(들쭉날쭉한 정도)가 250m로 나왔는데, 이건 평평한 가짜 데이터(0에 가까움)가 아니라 실제 산과 평야를 오르내리는 진짜 지형이라는 증거다.

경로(길 모양) 자체의 정확도도 별도로 검증했다(`scripts/pipeline/verify_route.py`) — 82개 마을을 OSM과 무관한 방법(Nominatim 지오코딩)으로 독립적으로 찾아, 우리가 이어붙인 경로에서 얼마나 떨어져 있는지 쟀다. **중앙값 126m**로 대부분 잘 들어맞았다(단, Nominatim 자체가 동명 마을 문제로 가끔 엉뚱한 좌표를 주기도 해서, 이상치가 나오면 그게 우리 경로 오류인지 Nominatim 오류인지 별도로 가려야 했다).

## 6. 2026-07(오늘): 갈림길 11곳에도 같은 방식을 써보려 한 시도와 한계

**시도**: 프랑스 길이 갈라졌다 다시 만나는 11곳(`data/forks.ts`)도 메인 경로처럼 "OSM에서 relation 찾기 → 이어붙이기 → 고도 계산" 방식을 쓸 수 있을지 확인했다.

**결과**: 조사한 변형 경로 이름 10개 중 최소 7개(에우나테·드라곤테·비야르 데 마사리페·산 실·비아 트라야나·프라델라·사모스)가 **OSM에 전용 relation이 없었다.** 메인 경로와 달리 이런 변형 경로들은 이름표가 붙은 relation이 아니라 이름 없는 일반 도로·오솔길 조각으로만 존재해서, 마을 하나하나를 따라가며 수동으로 조각을 추적해야 한다 — 이건 메인 경로 파이프라인보다 오히려 손이 많이 가는 작업이다.

**그래서 지금은**: `data/forks.ts`에 갈림길 11곳의 **구조**(변형 이름·경유 마을·계절 폐쇄·특징)는 가이드북·순례자 포럼 자료로 채웠지만, **정확한 거리·오르막·내리막은 전부 `null`(미확인)로 남겨뒀다.** 이 숫자를 지어내면 규칙 1(데이터를 지어내지 않는다)을 어기는 것이기 때문이다. 이 값들은 실측 도보 때 각 변형 경로를 실제로 걸으며 GPS 트랙(GPX)을 남겨야 채울 수 있다.

> 참고로 이번 조사 중 재미있는 기술적 문제도 있었다: 이 개발 환경에서 Overpass API에 파이썬(`urllib`)으로 직접 요청하면 매번 막혔는데, 같은 요청을 `curl` 명령으로 보내면 통과했다. 아마 요청 헤더나 접속 방식의 미세한 차이 때문으로 보인다.

## 8. 식당·바·카페 1,247곳 (2026-08-04) — 같은 방식을 숙소가 아닌 곳에 적용

`C_숙소카드교통데이터.md`의 숙소·안개지도 데이터는 사람이 Gronze.com 등을 읽고 옮긴 것(`GUIDEBOOK`)이지만, 이건 **Overpass API를 다시 호출**해서 만들었다는 점에서 이 문서(1~7절, 길·고도) 쪽 방법론과 같다.

- **조회 방식**: `amenity~"restaurant|bar|cafe"` 태그를, `data/towns.ts`에 이미 있는 마을 lat/lng(4절에서 확보한 그 좌표) 기준 반경 700m로 조회. 82개 마을 전부 조회 완료, 61곳에서 데이터 확보(21곳은 0건)
- **뺀 필드**: `opening_hours`. 표본 조사(팜플로나 광장 208곳 중 24곳=11.5%, 오르니요스 3곳 중 1곳=33%만 보유) 결과 신뢰할 수 없어 뺐다 — `exposed_stretches.ts`가 "바 개점 시각"을 같은 이유로 뺀 전례와 동일 판단(규칙 1). 이름·종류·좌표만 담는다
- **21곳이 0건인 이유가 불확실함을 숨기지 않는다**: 실제로 식당이 없을 수도 있지만, 마을 좌표가 4절의 "경로 위 km 비율 보간"으로 구했다는 점을 감안하면 좌표가 실제 마을 중심에서 살짝 벗어나 반경 밖으로 놓쳤을 가능성도 있다 — 둘 다 검증 못 함
- **재시도 전략**: `scripts/pipeline/build_restaurants.py`가 `overpass()`와 똑같은 패턴(curl subprocess, 미러 2개 순환, 재시도)을 재사용. 체크포인트 파일(`data/geometry/restaurants_checkpoint.json`)로 중단 후 재개 가능
- 상세 출처 표는 `D_원천출처목록.md` 1.1절
